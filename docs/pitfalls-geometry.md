# 几何踩坑 18 条（每条都是真踩过的）

> 这份清单来自 5 批次、23 个地块的实际交付。
> 每一条都是某个执行者**自己撞上、自己查到、自己修掉**的，不是我编的理论。
> **照着做能省半天。**
>
> 前提：渲染方式为「三渲二（cel shading） + 反向外壳描边 + 合并几何体」。

---

## 一、尺寸相关的四条

### #1 小于 5 cm 的东西不要做成几何体

`buildYard` 会给大部件加**反向外壳描边**。描边是**固定世界宽度**的，
比它细的东西渲染出来**几乎全是描边**——就是一团黑点。

→ 小于 5 cm 的细节靠贴图或不做。

### #2 3 cm 以下的细长条会变成虚线

瓦垄条做 3 cm 时几乎全是描边，远看是一串虚点。

→ 实测：市政厅把瓦垄**加厚到 8 cm** 才成线。**细条要么加厚，要么不做。**

### #3 给 box 传负尺寸 → 法线内翻 → 整面变成诡异深色

`MZ1 - PFACE` 这类表达式算成负数时，底面翻到里面去，而反向外壳描边把正面顶上来，
**整片立面读成深紫色**。市政厅第一版就这么废的。

→ 写一个 `bx(v) => Math.abs(v)` 包住**所有**尺寸参数。

### #4 顶点数 ≠ 三角数

`b.count` 是**顶点数**，`÷ 3` 才是三角形。面板读取时要除。

## 二、贴合相关的两条（最值钱的一组）

### #5 ⭐ 铁律：贴合的底边要**埋进去**，不要对齐

任何"底边贴着另一个面"的凸起，都会被描边描出一圈**牙齿/锯齿裙边**。
紫瓦尖顶、烟囱根、花盆底、台阶踏面、塔尖——**全部中招**。

19 号的解法：**把底边埋进下面那个面 1.3 m**，让它没有可见的边可描，
只剩一个干净的锥尖。之前 6 个版本都读成"悬空紫板"或"锯齿裙边"。

### #10 换个说法记同一条

"底边埋在下面那个面里" → 没有可见边 → 描边不产生裙边。
这与 #1 是一体两面：**描边惩罚所有"细"和"露边"的结构。**

## 三、圆、环、开口

### #6 `b.cyl` 必然封住两端 —— 所有"开口"的东西都不能用它

想做井口、水池、烟囱内壁、花盆口？用**一圈石块/柱体拼成环**。

15 号原话：第一版用实心 cyl，从任何高点看都像"**一口盖了石板的水缸**"；
改用环之后，压顶**又**用实心 cyl，等于**又给井盖了个盖子**。

→ 井口要透出黑色井底，靠"**深色衬板下探 + 底部水面盘 + 什么都不封口**"。

## 四、旋转与朝向

### #7 同时给两个轴的角度，默认欧拉序会让物体侧躺

默认 `XYZ` 序 = `Rx·Ry·Rz`，**即先 Rz 再 Ry 再 Rx** —— `rx` 在**偏航之后**绕世界 X 转。

后果：一个朝 90°/180° 的摊位，它的棚面会**侧躺**而不是前倾。
11 号（集市）就是这么做坏过一次。

→ 凡是"**先摆朝向、再让它倾斜**"的东西（棚面、斜撑、坡面、倒下的石碑），
都要显式指定顺序：`{ rx: tilt, ry: yaw, order: 'YXZ' }`（先绕局部 X 俯仰，再绕 Y 偏航）。

```js
b.box(w, h, d, { x, y, z, rx: tilt, ry: yaw, order: 'YXZ' }, color);
```

## 五、屋顶与山墙（造型特有）

### #8 十字交叉的屋脊上用通用 roof 函数，会漏一条棕色横杠

它总会画檐口封檐板，十字交叉时那块板正落在翼屋面表面上，俯视就是一条斜跨两片屋顶的棕杠。

→ 做十字/交叉屋顶时，**交叉那一侧不要用它，自己手写那一片屋面**（5 号遇到后自己写了）。

### #9 `gableRoof` 的 `bands` 是"整条深浅交替"，不是瓦缝数

想要瓦缝，请用 `bands: 1` 平涂 + 自己画缝条。

### #11 `gableWall` 内部会自动内缩 0.11，陡坡下不够 → z-fight

它的实现是 `rise = o.rise - inset * 1.9`，`inset` 默认 0.11。
缓坡上没问题，但 **55° 山墙坡**下这个内缩只留出 **0.02 m** 缝隙——
不足可靠分离深度值，**墙和瓦面争夺深度缓冲**，俯视看屋顶是一大片白色碎点。

12 号试了 4 个版本：

| 版本 | 结果 |
|---|---|
| 用默认 `gableWall` | 白碎点 |
| 居中棱柱 | 白碎点 |
| 抬高棱柱 | 从瓦面穿出，变成白楔子 |
| **留 0.28 m 明确间隙 + 端面用深木色** | ✅ 干净 |

→ 陡坡山墙不要直接用默认值。要么显式传 `inset: 0.28+`，要么自己写棱柱并留足间隙。
**白色端面在缝隙里会显得最脏，用深木色能压住。**

## 六、薄片与条纹

### #12 棚布/条纹这类薄片：用「等厚板并排对接」，不要「薄片+凸起」

11 号做条纹棚布时：

- 用薄片 → 前缘露出一排齿（#2 的复现）
- 做成一厚一薄的凸起板 → **接缝处又出齿**

→ 正解：**N 块等厚板并排、共用同一顶面、前缘压一道木檐条**，才干净。

## 七、相机与环境（非几何问题，但会造成同样的困惑）

### #13 每个单元的中心不一定是你想的位置

19 号的中心落在**两栋房子之间的巷子**里，预设的"贴地"相机会**塞进南宅墙上**。

→ 正确做法：用 `?eye=x,y,z&look=x,y,z`（世界坐标）直接摆相机做人视角验证，
并在报告里写清楚。**不要改共享的相机预设文件。**

### #14 掠射角下的阴影会有极淡横纹（shadow acne）

贴到墙前 10 cm 才会出现，关掉阴影就消失，正常视距看不到。
这是**预览页固定光照的属性，不是几何错误**——不要为此改模型。

### #15 数字预算会以"优化"的名义牺牲画面

原本给了"每块 ≤ 50000 三角"。结果是两个执行者把精力花在"砍花丛凑数字"上。
一块地的注释原文：*"花头太贵，所以数量控制在预算允许的范围内"*——
**一个虚构的限制直接决定了画面密度。**

→ 整镇 47 万三角跑 55 FPS，单块多几千个没有意义。**取消预算，只保留分段记账。**
分段列表的价值不是"算预算"，是"看清成本集中在哪"（例：15 号花坛 43,000 里有 26,000 是花头）。

### #16 软渲染会被误判成"模型太重"

| 参数 | 渲染器 | FPS |
|---|---|---|
| `--use-angle=swiftshader` | SwiftShader（CPU） | 13.5 |
| 什么都不传 | SwiftShader（CPU） | 13.3 |
| **`--use-angle=d3d11`** | **RTX 2080 Ti** | **60.3** |

→ 性能问题第一件事是**确认跑在真 GPU 上**，不是减面。

### #17 外接框 ≠ 真实轮廓

外接框比真实多边形**大 19.2%**，四角是斜切的路口。
用外接框散布花丛 → **花长在马路上**。

→ 散布一律用 `inPlot(px, pz, margin)`（真实多边形 + 边距）。

### #18 随机必须按单元播种

`Math.random()` 会导致每次重建画面都变 → 无法对比、无法复现 bug、无法验收。

→ 用 `ctx.rnd`（按单元 id 播种），并同时 reseed 全局流，让共享组件也保持一致。

## 附：三条元教训

1. **描边是这个系统里绝大多数视觉 bug 的源头。** 遇到"黑点/虚线/锯齿裙边/深色面"，
   先想"这个结构的尺寸或边是不是被描边惩罚了"。
2. **"看起来完成"和"真的建出来了"是两件事。** 静默失败（东西放在界外 →
   判点函数返回 false → 不报错不警告）是最阴的一类 bug。要有**空段检测**。
3. **每一条坑都应该进 BRIEF，并且带上"怎么判断"而不只是"怎么做"。**
   只写"要埋进去"不够，要写"贴合的底边会被描边描出牙齿，所以埋进去"。
