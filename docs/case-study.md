# 案例实录：23 个地块，5 天，从一栋房子到一座镇

> 这是一份**过程记录**，不是一个成功故事。
> 里面每个数字都来自项目的实测日志，包括失败的、被骗的、返工的部分。
> 目的：让别人看到"粗 → 细"这条路上，**具体在哪些点上会掉进坑里**。

---

## 0. 起点

目标：把一张 **6688×3764 的像素风俯视地图**（`town.png`）重做成一个
**小清新三渲二**风格的 three.js 3D 小镇。

用户的原始约束（很关键，直接决定了后面所有技术选择）：

- **不要用原地图的像素贴图**。地图只提供**布局**，颜色和画风自己定。
- 参照已有的两栋单体建筑当质量与风格的双重母本。
- **分块做，每块先给用户看，确认后再往下。**

> 最后这一条就是整套方法论的种子——它把"生成一座小镇"换成了"确认 23 次"。
> 但当时还没想到，要把它变成 23 个独立文件 + 一条验收闸。

---

## 1. 打样：一栋房子做到 37 万三角

第一步不是切镇，是**做一栋房子做到满意**。

- 产物：`town-cottage.html`（单栋蓝瓦小屋 + 暖房 + 院子），**37 万三角，790 KB**
- 副产品（后来证明比房子更值钱）：
  - 建造原语 `APP.Builder`（`b.box / b.cyl / b.sphere / b.gableRoof / b.gableWall …`）
  - 组件库 18 件（`railFence / stonePath / barrel / crate / planter / flowers / bench / lampPost / stoneSteps / stonePlinth / treeConifer / treeBroadleaf / treeBlossom / bush / grassTuft / rock / handcart …`）
  - 三渲二光照与描边的一套数值（`celMaterial` + 反向外壳描边 + 按部件大小 0.55 m 分段着色）

> **为什么先做一栋**：这一栋后来成了**所有派发的质量标准**。
> 派发提示词里不写"要精细"，写的是"打开 `yard_20.html`，你的密度不能比它低"。
> 前者不可执行，后者可执行。

**这一步还踩出一个关键判据**：描边是**固定世界宽度**的反向外壳，
所以比它细的东西渲染出来几乎全是描边 = 一团黑点。
这条规则后来写进了 BRIEF：**小于 5 cm 的细节不要做成几何体**。

## 2. 建模：从图到数据，然后**放弃全自动分割**

### 2.1 比例尺

以蓝瓦小屋为锚：地图上 591 px 宽的院子 ≈ 3D 里 16 米。

```
S = 591 / 16 = 36.938 px/m
```

→ 地图 6688×3764 px = 世界 **181 × 102 米**。

### 2.2 全自动分割建筑：**失败四轮**

| 尝试 | 失败原因 |
|---|---|
| 按色相分族（红/橙/绿/蓝/紫） | 树冠和屋顶在颜色空间里重叠 |
| 加"平坦度"判据（亮度方差） | 屋顶有瓦缝、烟囱、明暗过渡，树冠也有受光面 |
| 加"凸度"判据（contour/hull） | 手绘地图的房屋轮廓也不规则 |
| 检测"奶油色墙面" | 地图的墙色太灰，阈值调不出来 |

**最终方案：让用户手工框选。**

用户在截图上手绘了 23 个黑框。提取方法：

```
纯黑像素 (<70,70,70) → 从图像边界 flood fill 外部 → 剩下的是框内部
```

这个方法**对框互相接触、框线粗细不匀、手绘歪斜都免疫**——比连通域分析靠谱得多。

> **教训**：在这种"人眼一秒能分、算法很难分"的任务上，**人的 5 分钟 > 算法的 4 轮失败**。
> 分割不是目的，**拿到可用的边界数据**才是目的。

### 2.3 地面分类

关键理解：**地图只有 320×180 的信息量**，不必逐像素。

```
原始地图
  → cv2.resize 到 320×180（INTER_AREA，区域平均）
  → 按 hue/sat/val 分类为 G(草) / R(路) / S(石) / W(水) / F(林) / P(土)
  → 打补丁
  → scipy 算"到水的距离场"，base64 编码塞进 JSON
```

**结果：23 个地块，编号 0–22**，与用户框选一一对应。

> ⚠️ 这里后来爆过一次大的：**水体判据错了，整条河形状是废的**。
> 用户指出"右上角的花园和小岛不对"，我一开始去修地标（螺旋石墙、樱花树太大、木桥位置），
> 用户直接打断——因为**根因在地面分类的水/林边界阈值**，不在那些地标上。
> **教训：用户描述的是症状，你要找的是判据。**

## 3. 切分：切割单位选"街区"

**不要切成方格**，切成**有语义的单元**。

洞察：**道路网络已经把小镇切成不规则街区**，每个绿色街区就是它上面那栋房子的管辖范围
（连街区里的森林也算这个街区的，因为树属于它）。

于是规则是一行：`非路 且 非水` = 地块。

每个地块生成一条元数据：

```json
{ "id": 18, "centre": [x,z], "polygon": [[x,z],...],
  "bounds": {...}, "area_m2": 609, "ground": "sampler", "house": "..." }
```

23 个地块的面积范围 **273 ～ 1436 m²**。

> ⚠️ **`bounds`（外接框）比真实多边形大 19.2%**，四角是斜切的路口。
> 这个数字后来直接变成了一条硬约束：**散布必须用 `inPlot()`，禁止用 `bounds`**。
> 否则花会长在马路上。

## 4. 接口化：一地块 = 一个 JS 文件

```js
// src/yards/yard_18.js —— 一个地块的全部内容
APP.registerYard(18, function (b, ctx) {
    const { x, z, ground, inPlot, kit, rnd, colors } = ctx;
    b.box(4, 0.3, 2, { x, y: ground(x, z) + 0.15, z }, colors.stone);
});
```

**为什么不是 23 个独立 HTML**：23 份 HTML 合并必然冲突，而且每个人都会顺手改光照。

构建管线（`build.py`）：

```bash
python build.py cottage    # → town-cottage.html（单栋标杆）
python build.py town       # → town.html（整镇）
python build.py yard<N>    # → yard_<N>.html（单地块沙盘）
```

`build.py` 做四件事：读模板 → 按 `ORDER` 拼 `src/*.js` → **注入** `town_ground.json` /
`town_plots.json` / `yards/bounds.json`（早期硬写在模板里，导致改了数据不生效，后来改成构建时注入）→ 内联 three.js r155 并剥掉 deprecation 警告。

**注意 `town` target 是"自动发现" `src/yards/*.js` 的。** 这一条是被逼出来的：
原来手写清单，加了 `yard_4` 它也不会进镇子，而所有检查器都只遍历"存在的文件"，
所以**一个"根本没做"的地块对全部闸都是隐形的**。

## 5. 派发：六批，从 2 块到 5 块，中间换了执行者

| 批次 | 数量 | 地块 | 三角数 | 关键事件 |
|---|---|---|---|---|
| ① 子代理 | 2 | 15, 18 | 43,576 / 42,790 | **同时把工具链的坑全踩了一遍**。这两块成了样板 |
| ② 子代理 | 5 | 3, 4, 5, 10, 19 | 62,178 / 76,410 / 71,080 / 90,952 / 82,176 | 派发前**补基建**：任意 `yard<N>` 预览页、自动发现、`DISPATCH.md`、裁剪参考图 |
| ③ 子代理 | 4 | 11, 12, 17, 22 | 49,282 / 20,742 / 20,314 / 62,882 | 结束后 BRIEF 里累积了 **18 条坑**，每条都是真踩过的 |
| ④ 外援 CLI | 1 | 20 | **127,786** | **用户手动停掉子代理**，文件停在写到一半（第 424 行多一个 `}` → `missing ) after argument list` → 整页起不来）。我修好后，20 号成了**全项目密度标杆** |
| ⑤ 外援 CLI | 3 | 1, 2, 6 | 135,799 / 194,015 / 166,529 | 转折点：**发现 GPU 参数** `--use-angle=d3d11` |
| ⑥ 外援 CLI | 2 | 0, 8 | 108,286 / 97,431 | 并入整镇 **1,968,530 三角 / 60.5 FPS / 0 页面错误** |
| ⑦ 补交 | 5 | 9, 13, 14, 16, 21 | 147,081 / 62,619 / 159,509 / 74,538 / 43,918 | 9 号 = **"静默失败"的完整解剖**（见下） |

23 块中 7 号由单栋标杆 `town-cottage.html` 本体覆盖，所以派发的是 22 块。

**全部完成后：2,549,108 三角 / 60.1 FPS / 0 页面错误。**

### 5.1 从"子代理"换成"外部 CLI 外援"的三个理由

1. **子代理会被停掉**，留下半截文件（20 号那次）。外部 CLI 是独立进程，可控。
2. **外部 CLI 有完整 shell**（能跑 node / python、能自己构建预览页），子代理的工具受限。
3. **提示词可以写得很长很具体**（每份 ~6.2 KB），因为它是 `-p` 一次性输入。

代价：**一次只能跑一个**，跑完自己构建验收，再跑下一个。中途出错否则看不到。

> 还踩了一个环境坑：在某个 IDE/Desktop 的会话里调用该 CLI 时，父进程注入了
> `QODER_AGENT_SDK_ENTRYPOINT=sdk-ts` 等变量，CLI 误以为自己是 SDK 入口 →
> 直接 `sdk_invalid_args` 退出。解法：
> `env -u QODER_AGENT_SDK_ENTRYPOINT -u QODER_AGENT_SDK_VERSION -u QODER_SDK_AUTH_PAYLOAD_FILE -u QODER_SDK_CUSTOM_BASE_URL_BYOK <cli> ...`

### 5.2 ⭐ 20 号为什么做得特别好（可复用配方）

用户专门问过这个。复盘下来是**四样东西**，其它地块没给全：

| # | 配方 | 说明 |
|---|---|---|
| 1 | **给可运行场景，不给图片** | 让它用浏览器打开标杆 HTML。图片只能看"大概长什么样"，**场景能看"瓦垄多厚、窗框几层"** |
| 2 | **禁止搬代码，但指定重写** | 明说"不要搬 `house.js`"（它含 `MeshBasicMaterial`、烟雾粒子等 yard 系统不支持的东西），但"**照着造型和密度重写**" |
| 3 | **我先把尺寸量好告诉它** | "栅栏圈 17.1×15.4，你的矩形 24.2×15.6，所以深度刚好、宽度差 7.1，左右各扩 3.5" |
| 4 | **明说不要用错误解法** | "**不要把房子放大。** 房子就是原来那个尺寸，扩的是院子" |

同时要说清楚：那栋房子本身是**全项目最成熟的资产**（`house.js` 1356 行，反复打磨过），
20 号是在成熟设计上继续做，不是从零开始。

### 5.3 提示词必须单写

10 份提示词（每份 ~6.2 KB），**每份都单独看过参考图后写**。举两个真实差异：

> **plot6**：你的重点**不是把房子做得更大**，而是**把院子铺满**：水井、三个木桶、水槽、
> 木架、树、花坛、铺装路、石头。参照 20 号的完成度——它把 377 m² 铺满了，你要把 1436 m² 铺满。

> **plot21**：**这是唯一一块栅栏不完整的**——参考图里只有东侧一小段栅栏。
> 三面临路，所以边界附近不要放东西。**别自作主张围满一圈。**

**共用的四段**：质量标准（指向文件 + 三条可检验判据）/ 参考图里有什么（逐条列出）/
必踩的坑（表格摘要）/ 自检清单（7 条，每条都要真做）。

### 5.4 写死 GPU 参数（这一步很关键）

| Chrome 参数 | 渲染器 | FPS |
|---|---|---|
| `--use-angle=swiftshader` | SwiftShader（**CPU**） | **13.5** |
| 什么都不传 | SwiftShader（**还是 CPU**） | 13.3 |
| **`--use-angle=d3d11`** | **NVIDIA RTX 2080 Ti** | **60.3** |

写进提示词之后，所有交付都报 60 FPS——因为**它们终于跑在 GPU 上了**。
在此之前，几个 Agent 自报"13 左右，已经优化过了"。

> **Agent 不会告诉你"我在这台机器上看不清"，它只会尽力在错误的条件下交差。**

## 6. 验收：报告的每一个字都是真的，但东西还是错的

### 6.1 一次完整的"静默失败"解剖（9 号）

交付报告原文：

> All 18 sections built: plinth, walls, timber framing, purple main roof …
> fence along 23-gon polygon with south gate …
> `check_yards.py 9 --measure`: **PASS** (0 out-of-bounds vertices)
> Triangles: 83,754

**83,754 是真的，PASS 是真的，18 段也基本是真的——但栅栏一根柱子都没有。**

三个缺陷叠在一起：

| # | 缺陷 | 实测 |
|---|---|---|
| ① | `fenceAlongPolygon(1.08)` 生成 **187 个柱子点**，全部落在**多边形边线上** | 判内用 `inPlot(px,pz,0.06)` 要求离边 ≥ 6 cm；边线上的点距离 = 0 → **187 个通过 0 个** |
| ② | `push()` 内部才写 `marks` | 「建了 0 个东西的段」**连面板都不显示**，所以"18 段"里数不到它 |
| ③ | 旧检查器只查"存在的段" | 你没建，它就永远查不到 → **PASS** |

**修法：新增"空段检测"**——源码里 `b.mark('x')` 了、但一个三角都没建出来 → FAIL 并指名是哪个段。

> 这类 bug 的共同点：**不报错、不警告、报告里写着"完成"。**
> 它是最值得投入工具去抓的一类。

### 6.2 检查器自己被骗过三次

| # | 假在哪 | 后果 |
|---|---|---|
| ① | docstring 写着 `bounds — any vertex outside the plot polygon?`，`SLACK = 1.6` 也定义了，**函数体里根本没用** | 子代理原话：**"如果当时真的超界，我会带着 PASS 交上去。"** |
| ② | 预览页"出界 0"——漏了 `NaN` 判断，`NaN > x` 恒 `false` | 计数器恒为 0 |
| ③ | 故障注入脚本写错函数签名（`sphere(r, o, color, ws, hs)`，第二个参数是**位置对象**，我传了三个数字），**函数一声不响什么都没建** | 三角数没变、检查器 PASS——**差一点把"注入没生效"当成"限制已取消"** |

**正确做法：故障注入 + 自校验。**

```
注入前基线：43,576 三角
注入 900 个 sphere（每个 140 三角）→ 期望 ≈ 169,576
实测 151,576（= 旧上限的 3 倍）→ 检查器依然 PASS、退出码 0   ✅ 上限真的取消了
若实测没比基线多 2 万 → 报 INVALID TEST，而不是 PASS        ← 关键
```

### 6.3 验收者（我）也误判过两次

| 误判 | 真相 |
|---|---|
| "20 号整个地块歪在边界框外，房子在框外" | 查俯视图：**两栋房子完整落在多边形内**，那条 40 米长的"越界"是**该地块的针叶林**。我把森林误读成了越界。→ **多视角交叉核对，单张等距图容易误判** |
| "10 号石材色差太大"（像素极差 154，铺装只有 65） | 调色板极差其实 **75.6**。池壁是**圆柱面**，受光面→背光面亮度自然横跨一大段；铺装是**平面**所以只有 65。而且 15 号用的是**完全相同的一组色**。→ **量颜色要量调色板，不是量渲染后的像素；曲面明暗变化不是色差** |

### 6.4 固定的验收动作

```bash
node --check src/yards/yard_<N>.js
python build.py yard<N>
python tools/check_yards.py <N> --measure    # 白盒：边界 + 真三角数 + 空段
python tools/review_wave.py <N> --shots      # 黑盒：独立重数 + 截图
# 然后自己看图
```

其中 `review_wave.py` 的价值是**独立地**遍历 `scene.graph` 重数三角形，和面板数字比对——
**两套独立实现算出同一个数**，才算可信。

### 6.5 交付格式里强制的那一条

**最有价值的部分不是"我做了什么"，是"哪里没做好"。**

好的交付原文：

> **最没把握：天窗。** 它现在干净了（无锯齿裙边、无穿出），但代价是必须紧贴主脊……
> 要放低就必须让后端露出来，我没找到既低又干净的做法，**选择了"干净"**。

这种句子能让人**立刻决定**：接受还是返工。所以交付格式里必须强制这一项，
并明写「**不许虚报。没做就写没做，不确定就写不确定。**」

## 7. 合并时的容错

一个半成品文件已经是 `registerYard(N, ...)` 了，只是内部有未定义变量 →
一打包就运行时抛错 → **整个小镇白屏**（17 号时撞到过一次）。

```js
try {
    res = APP.buildYard(parseInt(pid, 10), info, scene);
} catch (e) {
    console.error('yard ' + pid + ' failed to build — skipped:', e);
    town.brokenYards.push({ id: +pid, error: String(e && e.message || e) });
    continue;   // ← 一个地块坏掉，只损失那一块
}
```

再加覆盖率检查：**`bounds.json` 里有、但 `src/yards/` 里没有对应模块的地块 → 报警。**
因为其它所有闸都只遍历"存在的文件"，一个"根本没做"的地块对它们完全隐形——
它在镇子里就是一个 **196 三角的灰盒子**，看起来非常正常。

## 9. 如果重做一次，会在第一天就做对的事

1. **先写"空段检测"再派发。** 它抓的是"看起来完成、实际什么都没建"这一类 bug，成本极低。
2. **先做一次故障注入，证明检查器会 FAIL。** 否则你无法区分"通过"和"没在检查"。
3. **派发前补基建**：任意单元预览页 + 自动发现 + 派发说明。否则每个 Agent 都会卡在同一处。
4. **第一天就把环境参数写进提示词**（GPU / 版本 / 命令）。不写，收到的所有性能报告都是假的。
5. **不要给数字预算。** 它会被用来牺牲画面换数字。
6. **交付格式第一天就加上"哪里没做好"。** 这一条的收益比任何自动化检查都高——它让人主动暴露问题。
7. **多视角截图是验收入口，不是可选步骤。** 单张等距图会让人把森林读成越界。
