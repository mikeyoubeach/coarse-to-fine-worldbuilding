# 验收协议 · 交付格式

> 验收是整套方法里**最容易自欺**的一步。
> 这一份文档的全部内容可以压成一句话：
> **报告只能当参考，数字必须自己复现，图是唯一不会撒谎的东西。**

---

## 零、三条铁律

**1. 执行者说"完成"，等于什么都没说。**
它不是在骗你——多数时候它**真心认为自己完成了**。它跑了构建、看了图、没看到明显错误。
但"没看到错误"和"没有错误"是两个东西。

**2. 闸必须有退出码，且必须做过故障注入。**
一个从没 FAIL 过的检查器，和一个永远打印 PASS 的检查器，在你看不到区别。
案例里先后有 5 个"看起来在工作"的检查器实际什么都没检查（详见 case-study §6.2）。

**3. 自己构建，自己跑闸，自己看图。三件事一件都不能省。**
跳过构建 → 你验的是旧版本。跳过闸 → 你验的是"感觉"。跳过看图 → 你验的是报告。

## 一、验收动作（固定顺序，不许跳）

```bash
cd <工作目录>

# ① 重新构建 —— 永远不要用执行者留下的产物验收
python build.py unit<N>

# ② 跑闸，看退出码（不是看它打印了什么）
python tools/check_units.py <N> --measure
echo "exit=$?"

# ③ 覆盖检查 —— 有没有"根本没做"的单元
python tools/check_units.py --town
```

```
# ④ 看图：至少五张
浏览器 --use-angle=d3d11 "unit_<N>.html?hud=0"                # 总览
浏览器 "unit_<N>.html?hud=0&eye=<x>,0,<z>&look=<x>,0,<z>"      # 正俯视
浏览器 "unit_<N>.html?hud=0&eye=<x>,3,<z>&look=..."            # 人眼高度
浏览器 "unit_<N>.html?hud=0&eye=...&fov=30"                    # 推到最近
# ⑤ 打开标杆文件，做同样的事，对比密度
```

> **④ 的相机位置要你自己算**：单元的预设相机可能塞在墙里、可能正对巷道。
> 用 `?eye=x,y,z&look=x,y,z` 直接给世界坐标。**不要改共享的预览页。**

## 二、闸要检查什么

| # | 检查 | 怎么判 | 为什么必须有 |
|---|---|---|---|
| 1 | 卫生 | 静态：禁用 API、必填调用、颜色是否出调色板 | 便宜、快、能挡掉 90% 的"顺手" |
| 2 | 边界 | 驱动真实预览页，**遍历所有顶点**判多边形（含容差） | 只是"看着没出界"是不够的 |
| 3 | 空段 | 源码 `mark('X')` 了，但建成的段里没有 `X` | **最阴的一类 bug** |
| 4 | 覆盖 | 数据表里的单元集合 vs 实际模块集合 | 没做的单元对其它所有检查都不可见 |
| 5 | 实测量 | 三角数、FPS | **只报告，不设上限** |

### ⚠️ 第 3 条为什么必须单列

示例项目的 `utils.js` 只在 `push()` 内部才登记一个分段，
所以一个"建了 0 个东西"的分段**不会以 `tris: 0` 出现，而是彻底消失**。

后果：9 号的围栏整段没建出来，构建成功、闸 PASS、报告写着"围栏已完成"。
只有对比"源码里 mark 了什么" vs "运行时建成了什么"才能发现。

```python
declared = re.findall(r"b\.mark\(\s*['\"]([^'\"]+)['\"]\s*\)", src)
missing  = [d for d in declared if d not in built_marks]
```

### ⚠️ 第 4 条为什么必须单列

其它所有检查都**遍历已存在的模块**。一个"没有模块"的单元对它们完全不可见：
不进入单元闸、不报错（灰模渲染得完美）、也不进 `broken` 列表（因为从未被尝试）。

**只有把两个集合相减**才能发现它。

## 三、故障注入：验证你的闸真的会 FAIL

**每个闸上线前，至少做一次。** 做法极其简单，而且**必须做**：

| 闸 | 注入方式 | 期望 |
|---|---|---|
| 边界 | 在模型里塞一个坐标明显在单元外的盒子 | FAIL，且报出顶点数 |
| 空段 | 把某一段的内容整段注释掉，只留 `mark()` | FAIL，且点名那一段 |
| 覆盖 | 临时改名一个单元文件 | FAIL，且列出缺失的 id |
| 卫生 | 插入一行 `Math.random()` | FAIL，且指名 |

注入完**恢复，再跑一遍确认 PASS**。

> **案例里的真实教训**：一个检查器的 docstring 里写着"检查边界"，
> 但代码里从来没跑过边界检查——于是它连续 3 个批次给越界的单元发了绿灯。
> 一个说谎的检查器比没有检查器更糟：它让你停止怀疑。

## 四、验收者（你）也会误判，两个真实案例

**误判 1：把"看起来脏"读成"模型坏了"。**
某个单元掠射角下的墙面有极淡横纹，判定为几何错误 → 让执行者返工两轮。
真相是 shadow acne，预览页固定光照的属性，正常视距根本看不到。
**教训**：先做一次对照（关掉阴影看看还在不在），再下结论。

**误判 2：把"跑得慢"读成"模型太重"。**
13 FPS → 要求减面。真相是截图用了 CPU 软渲染（SwiftShader）。
换 `--use-angle=d3d11` 后同一份几何 **60.3 FPS**。
**教训**：性能问题第一件事是确认跑在真 GPU 上。

> 两次误判的共同点：**我用一个未经对照的观察，直接去指挥别人改东西。**
> 对照实验的成本，永远低于一轮返工。

## 五、交付格式（强制）

```markdown
## <N> 号交付

1. 建了哪几段（每段三角数）
2. 主要尺寸
3. 实测三角数 / 出界顶点（必须 0）
4. 从参考图读到的 vs 自己设计的
5. 和标杆比：哪些做到、哪些没做到、为什么
6. 哪一段最没把握 / 什么没做完
```

### 第 6 项是整份报告里最有价值的一行

不是客套话。它直接决定验收者是**接受**、**返工**还是**改设计**。

好的样子：

> **最没把握：天窗。** 它现在干净了（无锯齿裙边、无穿出），但代价是必须紧贴主脊。
> 要放低就必须让后端露出来，我没找到既低又干净的做法，**选择了"干净"**。

坏的样子：

> 总体完成，效果良好，符合预期。

第二种没有任何信息量——它和"我什么都没检查"无法区分。

### 反向要求：验收者也要给"为什么"

返工时不要只说"不好看"。要说：

- ❌ "屋顶还是不行，再改改"
- ✅ "俯视看屋顶有一大片白碎点。怀疑是 55° 山墙下 `gableWall` 的默认内缩
  只留 0.02 m，深度缓冲在打架。显式传 `inset: 0.28` 试一次。"

**给出假设，执行者才有方向。** 只说"不行"会让它开始瞎试，而瞎试的产物通常更差。

## 六、验收清单

```
[ ] 自己重新构建过（没用执行者的产物）
[ ] 闸的退出码是 0（不是"打印了 PASS"）
[ ] 看到过闸 FAIL 的样子（故障注入过一次）
[ ] 空段检查覆盖到了（不是只看三角总数）
[ ] 覆盖检查跑过（"没做"的单元能被发现）
[ ] 至少 5 张图，含正俯视 + 人眼高度 + 推近
[ ] 打开过标杆做对比
[ ] 报告第 6 项写了真话
[ ] 任何异常都先做了对照实验，再下结论
```

## 七、一句话

> **你能复现的才算数。**
> 报告是线索，闸是下限，图是证据。
