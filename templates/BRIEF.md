# 单元任务书（BRIEF）· 通用模板

> **怎么用**：把 `<...>` 换成你的领域词（地块 / 页面 / 章节 / 关卡 / 模块）。
> 这份是**所有单元共用**的，派发时每个执行者都要读。
> 每一节都删了就会出事——尤其是「四·六 坑清单」和「六 自检」。
>
> 本文示例是 3D 场景，但结构对任何"大量单元、每单元要精细"的任务都成立。

---

## 零、你只能改这一个文件

```
<工作目录>/src/<units>/<unit>_<N>.js
```

**其它任何文件都不许改**，包括共享的预览页、光照、相机预设、构建脚本。

**为什么**：并行执行时，一个人对共享文件的"顺手优化"会毁掉其它所有人的结果。
如果你觉得工具不合用，**绕过去，并在报告里说清楚**——这是正确做法。

---

## 一、你要写出的结构

```js
APP.registerUnit(<N>, function (b, ctx) {
    const { x, z, ground, inPlot, kit, rnd, colors } = ctx;

    b.mark('plinth');           // 分段记账（强烈建议）
    b.box(6, 0.35, 5, { x, y: ground(x, z) + 0.175, z }, colors.stone);

    b.mark('wall');
    // ...
});
```

一次调用、一个函数、没有第二个入口。文件之间**零依赖**。

---

## 二、`ctx` 里有什么

| 字段 | 说明 |
|---|---|
| `x, z` | 单元中心世界坐标 |
| `polygon` | **真实轮廓**多边形 |
| `inPlot(x, z, margin)` | 判点是否在单元内（含边距）。**散布必须用它** |
| `bounds` | 外接框。⚠️ **别用来散布**——比多边形大 19.2% |
| `ground(x, z)` | 真地形高度采样。**不要写死 `y = 0`** |
| `rnd` | 按单元播种的确定性随机。**不要用 `Math.random()`** |
| `kit` | 现成组件（围栏/石路/桶/花箱/长椅/路灯/台阶/树/灌木/草簇/岩石…） |
| `colors` / `pal` | 调色板。色系要统一 |
| `area` | 单元面积（m²） |
| `house` | 本单元已有的主体（可能为 null） |
| `slack` | 允许多边形外溢的容差（示例值 1.6 m） |

**`kit` 用之前先看实测数据**——有些组件很贵（比如某些树的细分很高），
不是不让用，是让你知道成本花在哪。

## 三、硬性约束

| 约束 | 值 | 怎么查 |
|---|---|---|
| 边界 | 顶点必须在**多边形**内，容差见 `ctx.slack` | 白盒闸会实测，超了直接 FAIL |
| 文件 | 只能改自己那一个 | — |
| 材质 | 不许自己 `new Mesh` / `new Material` | 静态检查 |
| 随机 | 用 `ctx.rnd`，不许 `Math.random()` | 静态检查 |
| 颜色 | 色系统一 | 静态检查（超出调色板会提示） |
| 几何 | 全部推给 `b` | — |

### 关于"要不要给三角数预算"

**示例项目里最终取消了。** 理由：

- 约束本身不成立（整镇 47 万三角跑 55 FPS，单单元多几千个没有性能意义）
- **它会改变设计决策**：执行者会把精力花在"砍装饰凑数字"上，而不是"画面好不好看"

> **如果你的领域要设上限，先问一句：这个上限是真实约束，还是我编的？**
> 如果是编的，它一定会被用来牺牲质量换合规。

`b.mark('段名')` 仍然建议用——**用途是理解成本构成，不是删东西**。

## 四、领域硬知识（几何/渲染类，示例）

**1. 小于 5 cm 的东西不要做成几何体。** 描边是固定世界宽度，比它细的东西渲染出来几乎全是描边 = 一团黑点。

**2. `b.count` 是顶点数，不是三角形数。** ÷3 才是三角形。

**3. 旋转顺序默认 `XYZ`（= 先 Rz，再 Ry，再 Rx）。** "先摆朝向、再倾斜"的东西要显式传 `order: 'YXZ'`。

**4. 球体默认细分 `(10,7)` ≈ 140 三角/个。** 装饰小球显式传 `(5,3)`（20 三角）。

**5. 圆柱必然封住两端。** 所有"开口"的东西（井口/花盆/烟囱内壁）用一圈块拼成环。

**6. 贴合的底边要埋进去，不要对齐。** 否则被描边描出一圈锯齿裙边。

## 五、风格参考（**这是最重要的部分**）

参考必须是**可运行的文件**，不是截图。

| 参考 | 学什么 |
|---|---|
| `<标杆文件 A>` | **密度与完成度的硬标准** |
| `<风格文件 B>` | 硬边、瓦垄、木构分层、窗的画法 |
| `<同类小件 C>` | 同类小单元的高效处理（三角数很低但看着够） |

**⚠️ 不要学**：`<某个明确的反例>` —— 说明它哪里不对（示例：它有水彩雾感和柔焦，我们要清晰硬边）。

**"打开标杆文件对照"是所有自检里最有效的一条。** 因为"精细"这个词没有判据，
而"密度不能比它低"有。

## 六、你的自检工具

### 构建与预览

```bash
python build.py unit<N>            # → <unit>_<N>.html，双击打开（或浏览器打开）
python tools/check_units.py <N> --measure   # 必须 PASS
```

### 相机三种摆法

1. **URL 参数（最可靠，可复现）**：`<unit>_<N>.html?eye=x,y,z&look=x,y,z&hud=0`
2. **API**：`window.__setCam__({...})`
3. **键盘预设**：`1` 总览 / `2` 俯视 / `3` 西南 / `4` 东南 / `5` 贴地 / `6` 特写 / `R` 复位

> 预设相机在单元中心位置特殊时（在墙里、在两栋之间）会穿墙。
> **这不是你的错，也不要改共享的预览页**——用 URL 参数直接给世界坐标。

### 必须做的自检

1. `1` 总览 —— 整块完整入画，和参考图对比布局
2. `2` 正俯视 —— 位置、对称、朝向
3. **正面正投影** —— 和参考图对比门高/窗位/台基/台阶
4. **人眼高度** —— 有无悬空、穿帮
5. **推到最近** —— 接缝、z-fighting
6. **打开标杆文件对照 —— 密度够不够？**
7. `check_units.py <N> --measure` —— **PASS，出界 0**

**每一条都要真的做。** 报告里会被问到，而验收者会自己核对。

## 七、交付格式

```markdown
## <N> 号交付

1. 建了哪几段（每段三角数）
2. 主要尺寸（开间/进深/檐高/脊高 …）
3. 实测三角数 / 出界顶点（必须 0）
4. 从参考图读到的 vs 自己设计的
5. 和标杆比：哪些做到、哪些没做到、为什么
6. 哪一段最没把握 / 什么没做完
```

**⚠️ 不许虚报。没做就写没做，不确定就写不确定。**

第 6 项是**最有价值的一项**。写成这样最好：

> **最没把握：天窗。** 它现在干净了（无锯齿裙边、无穿出），但代价是必须紧贴主脊。
> 要放低就必须让后端露出来，我没找到既低又干净的做法，**选择了"干净"**。

这种句子能让验收者**立刻决定**接受还是返工。写"总体完成，效果良好"没有信息量。
